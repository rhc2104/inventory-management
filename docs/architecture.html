Architecture Overview

Factory Inventory Management System

A full-stack demo application: a Vue 3 single-page app talks to a stateless Python FastAPI service that serves read-only mock data loaded from JSON files at import time. There is no database, no persistence layer, and no authentication.

Vue 3.4 SPA FastAPI + uvicorn 7 JSON data files 14 HTTP endpoints ~8,400 lines of app code 40 backend tests

System Architecture

Three layers, each with a single responsibility. Both processes run locally and are started independently; the frontend hardcodes the backend origin rather than proxying through Vite.

Data Flow — A Filter Change

The four global filters (Time Period, Warehouse, Category, Order Status) drive every view. Filtering is server-side; the client sends the filter state as query params and re-renders from the response.

  1. User changes a filter in FilterBar.vue
    The control is bound to a ref inside useFilters.js. Because those refs are declared at module scope, every component that calls useFilters() shares one instance — no provide/inject or store needed.
  2. The active view watches filter state and calls getCurrentFilters()
    This maps UI names onto API names — selectedLocation becomes warehouse, and selectedPeriod becomes month only when it isn't 'all'.
  3. api.js builds a URLSearchParams and issues the GET
    Each method drops any filter equal to 'all' rather than sending it, so the query string carries only active filters.
  4. FastAPI receives optional query params and filters in Python
    Handlers run list comprehensions over the in-memory data. Comparisons on category and status are lowercased for case-insensitive matching; the original lists are never mutated.
  5. Pydantic validates the response against response_model
    A mismatch between JSON data and the declared model surfaces here as a server-side validation error — which is why model updates have to follow any change to the data shape.
  6. The view assigns the payload to a ref; computed properties derive the rest
    Raw responses live in refs (allOrders, inventoryItems); every table, KPI, and SVG chart is a cached computed property downstream of them.

Notable Findings

Observations from reading the code that aren't apparent from the README, and that would otherwise surprise someone extending the system.

The client calls six endpoints the backend does not implement
api.js defines methods for /api/tasks (GET, POST, DELETE, PATCH) and /api/purchase-orders (POST, GET), but no route in main.py matches any of them. App.vue calls getTasks() on mount, so every page load fires a request that returns 404 — confirmed live against the running server. The failure is silent: it's caught and logged to the console, and the Tasks modal still works because it falls back to merging in the mock task list from useAuth. The two purchase-order methods are never called at all.
Purchase-order write support is modeled but not wired up
The backend declares PurchaseOrder and CreatePurchaseOrderRequest Pydantic models and loads purchase_orders.json, yet exposes no route that creates or returns them. Combined with the unused client methods, this looks like a feature that was scaffolded on both ends but never connected in the middle.
Backlog.vue is unreachable
The view exists and fetches data, but main.js registers no route for it and nothing imports it. Backlog data does reach the UI — through Dashboard.vue and BacklogDetailModal.vue — so the standalone page appears to be superseded rather than pending.
Data is immutable at runtime, and this is load-bearing
mock_data.py runs json.load() once at import. Handlers filter over copies and never mutate the globals, so the API is effectively idempotent and every restart resets state. Any write feature would need to decide where mutations live.
Development-only CORS and no authentication
The service sets allow_origins=["*"] together with allow_credentials=True and has no auth, rate limiting, or input sanitization. Appropriate for a local demo; a blocker for anything deployed. The frontend also hardcodes http://localhost:8001/api rather than reading an environment variable or proxying through Vite.
Date filtering is substring matching, not date parsing
filter_by_month() tests whether "2025-03" appears anywhere in the order_date string, and the quarterly report chains if/elif checks over hardcoded month literals. Both work only for 2025 and would need reworking for any other year or a real date column.
